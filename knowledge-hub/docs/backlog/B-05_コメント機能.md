## 背景・目的

ナレッジ記事に対する補足・質問・訂正を残せるようにし、記事を起点とした知識の集約を進める。コメントも記事と同様に投稿者本人が編集・削除できるよう、**コメント単位のパスワード**で保護する。

## 要件概要（ユーザー要望）

- 記事にコメントを投稿できる
- コメントは編集・削除が可能。投稿時にパスワードを設定し、編集・削除時にそのパスワードを要求する（B-02 の記事パスワードと同じ方式）

## 仕様の方向性（案・未確定）

- **データモデル**: コメントは新エンティティ（記事ID・本文・投稿者名・パスワードハッシュ・作成/更新日時）。現行テーブルは単純キー（PK: `id` のみ）のため、持ち方は [2]Plan で確定する
  - 案A: 既存テーブルに別アイテム種別として同居（シングルテーブル設計。キー設計の変更が必要になる可能性）
  - 案B: コメント専用テーブルを追加（PK: `articleId`、SK: `commentId` 等。**プロビジョンドキャパシティの合計を無料枠 25RCU/WCU 内に収める**こと）
- **API**: `/api/articles/{id}/comments` 配下に CRUD を追加。パスワード検証・エラー形式（`{"message": ..., "errors": [...]}`）は B-02 と同一方式
- **フロントエンド**: S-02 記事詳細にコメント一覧・投稿フォーム・編集/削除導線を追加。SSR + Server Actions 構成を維持し、クライアントコンポーネントは最小限に留める
- **記事削除との整合**: 記事を削除したとき配下のコメントをどうするか（連鎖削除の要否）を決める
- **B-01 との連携**: 管理ユーザーはパスワードなしで任意のコメントを削除できる（不適切コメント対応）

## 影響範囲（想定）

- backend: コメントのエンティティ・リポジトリ（local/prod 両プロファイル）・サービス・コントローラ新設、記事削除時の連鎖処理
- frontend: S-02 のコメント UI 一式（Server Actions 含む）
- infra: `template.yaml` へのテーブル or キー設計変更（**キャパシティ配分はリスク Critical 扱いになり得る**）
- docs: 設計書（機能・API・データ・モジュール構成）、テーブル定義書、画面設計書（S-02）、README（API 仕様）

## ai-flow [1]要件確認で確定させる事項

- コメントの項目: 投稿者名（任意・B-03 と同方針）を持つか、本文の最大文字数
- コメントのパスワードは必須か任意か（B-02 の決定に合わせるか）
- 記事削除時に配下コメントを連鎖削除するか
- コメントの表示順（古い順 / 新しい順）と件数上限・ページングの要否
- 編集済みコメントの表示（「編集済み」表示の要否）
- 管理ユーザーによる削除の範囲（削除のみか、編集も可能か）※B-01 導入済みの場合
