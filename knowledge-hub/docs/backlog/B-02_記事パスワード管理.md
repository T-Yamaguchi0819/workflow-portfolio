## 背景・目的

現状は誰でも他人の記事を編集・削除できてしまう。記事の**追加時にパスワードを設定**し、以後の編集・削除にそのパスワードを要求することで、投稿者本人以外による改変を防ぐ。

## 要件概要（ユーザー要望）

- 記事の追加段階で、編集・削除の実行用パスワードを設定するようにする
- 編集・削除の実行時にパスワードの入力を求め、一致した場合のみ実行する

## 仕様の方向性（案・未確定）

- **データ**: `Article` にパスワードの**ハッシュ**を保持する属性を追加する（平文保存は禁止。BCrypt 等）。ハッシュは `ArticleResponse` に**絶対に含めない**
- **API**: 更新（PUT）・削除（DELETE）のリクエストでパスワードを受け取り、サーバ側で検証する。不一致時は 403 を返し、エラーレスポンスは既存の `{"message": ..., "errors": [...]}` 形式を維持する
- **フロントエンド**: S-03 作成フォームにパスワード入力欄を追加。編集・削除時はパスワード入力（削除は既存の confirm ダイアログとの統合を検討）。SSR + Server Actions 構成を維持
- **既存記事の扱い**: パスワードなしで作成済みの記事（シードデータ・dev/prod の既存データ）をどう扱うかの方針が必要（移行措置）
- **B-01 との連携**: 管理ユーザー導入後は、管理者はパスワードなしで編集・削除できる（どちらを先に実装しても、後発側でバイパス処理を要件に含める）

## 影響範囲（想定）

- backend: `Article`・`ArticleRequest`（作成時のパスワード）・更新/削除 API の検証ロジック、`ApiExceptionHandler`（403 系の追加）
- frontend: S-03/S-04 フォーム、削除導線、Server Actions（`actions.ts`）
- infra: DynamoDB 属性追加のみならテーブル定義変更は不要（スキーマレス）だが、テーブル定義書には属性を追記
- docs: 設計書（API・データ）、テーブル定義書、画面設計書（S-03/S-04）、README（API 仕様）

## ai-flow [1]要件確認で確定させる事項

- パスワードは**必須**か任意か（任意の場合、未設定記事は誰でも編集・削除可のままか）
- パスワードの形式要件（最小文字数・文字種）
- 既存記事（パスワードなし）の移行方針: 編集・削除不可にする / 誰でも可のままにする / 初回編集時に設定させる
- パスワードの変更・再設定手段の要否（忘れた場合の救済は B-01 管理者対応でよいか）
- 削除時の UI フロー（confirm ダイアログ＋パスワード入力の統合方法）
- 検証失敗時のステータスコード（403 想定）とメッセージ文言
