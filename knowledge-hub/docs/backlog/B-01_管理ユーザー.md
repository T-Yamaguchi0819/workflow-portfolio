# B-01: 管理ユーザー（全記事の編集・削除が可能なユーザー）

| 項目 | 内容 |
|------|------|
| ステータス | 未着手 |
| 種別 | 改善・機能追加 |
| 対象画面/機能 | 全画面（ログイン導線の追加）、記事編集・削除処理 |
| 依存 | なし（B-04 トップ表示固定の前提。B-02/B-05 のパスワードバイパスにも関係） |

## 背景・目的

現状は誰でもすべての記事を編集・削除できる。B-02（記事パスワード管理）導入後は投稿者以外が記事を触れなくなるため、不適切な記事の削除や記事のメンテナンスを行える**管理権限**が必要になる。また B-04（トップ表示固定）のような「管理者だけが行える設定操作」の土台にもなる。

## 要件概要（ユーザー要望）

- 管理ユーザーを作成・設定できるようにする
- 管理ユーザーは**全記事の編集・削除**が行える（B-02 導入後は記事パスワードなしで実行できる）

## 仕様の方向性（案・未確定）

- **認証方式**: 無料枠維持の制約があるため、まずは「単一の管理者アカウント」を最小構成で実現する案を第一候補とする
  - 案A: 管理者パスワードを環境変数（Lambda 環境変数 / `.env`）で保持し、ログインでセッション（署名付き Cookie）を発行する。ユーザーテーブル不要
  - 案B: DynamoDB にユーザーアイテムを持ち、複数管理者・パスワード変更に対応する
  - Cognito 等のマネージド認証は構成が重くなるため、採用するなら無料枠と SSR（Next.js Server Actions）との相性を [2]Plan で評価する
- **フロントエンド**: SSR + Server Actions 構成を維持する（SPA 化禁止）。ログイン画面を新設し、管理ログイン中は編集・削除 UI を常時表示する
- **バックエンド**: 管理者として実行された編集・削除は所有チェック（B-02 のパスワード検証）をバイパスする。API の認可をどの層（API Gateway / Spring / Server Actions）で行うかは [2]Plan で確定
- **秘密情報**: 管理者パスワード・署名鍵のハードコード禁止（環境変数経由、`.env` は git 管理外）

## 影響範囲（想定）

- backend: 認証エンドポイントまたはトークン検証、編集・削除の認可判定
- frontend: ログイン画面（画面追加 → `docs/screens/` に採番・新設）、セッション管理、管理者向け UI 表示切替
- infra: Lambda 環境変数の追加（`template.yaml`）。案B なら DynamoDB テーブル定義にも影響（無料枠内に収めること）
- docs: 設計書（機能・画面・API・データ）、画面設計書、README（API 仕様）

## ai-flow [1]要件確認で確定させる事項

- 管理ユーザーは**1アカウント固定**でよいか、複数作成・管理（作成 UI）まで必要か
- 認証方式（案A: 環境変数＋セッション / 案B: DynamoDB ユーザーテーブル / その他）
- セッションの有効期限・ログアウトの要否
- 管理ユーザーができる操作の範囲: 全記事の編集・削除のみか、B-04 のトップ固定設定・B-05 のコメント削除も含むか（依存機能の導入時期との整合）
- ログイン失敗時の挙動（試行制限の要否）
