## 概要

開発段階のブランチ（`ai/*`）を AWS 上の**共有 dev 環境**へデプロイ可能にし、ai-flow の [6]動作確認を「ローカル起動」ではなく「デプロイ済み dev 環境」で行えるようにする。

- バックエンド: SAM スタック `knowledge-hub-dev` を新設し、`ai/**` への push で GitHub Actions が自動デプロイ
- フロントエンド: Amplify Hosting の**自動ブランチ作成**（パターン `ai/*`）でブランチごとにデプロイし、ブランチ削除で自動消滅。branch 用環境変数 `API_BASE_URL` を dev API に向ける
- dev 環境は共有1本。複数タスク同時進行時は後勝ち（ユーザー許容済み）

## 詳細要点

現状調査に基づく変更対象と要点:

1. **`knowledge-hub/infra/template.yaml`** — 物理リソース名が固定（`knowledge-hub-articles` / `knowledge-hub-api` / `knowledge-hub-http-api`）のため、同一テンプレートから dev スタックを作ると名前衝突する。`${AWS::StackName}` ベースの命名に変更する。**prod スタック名は `knowledge-hub` なので、`${AWS::StackName}-articles` 等の解決結果が現行物理名と完全一致するよう命名する**（リソース再作成なしが絶対条件）
2. **`knowledge-hub/infra/samconfig.toml`** — 現在は `default` 環境（stack_name=knowledge-hub）のみ。`[dev.deploy.parameters]`（stack_name=knowledge-hub-dev）を追加し、`sam deploy --config-env dev` で切替可能にする
3. **`.github/workflows/deploy.yml`** — 現在は main push のみ。トリガーに `ai/**` を追加し、ブランチにより prod（`knowledge-hub`）／dev（`knowledge-hub-dev`）へ振り分ける。スモークテストの対象スタック名も振り分ける
4. **`knowledge-hub/infra/github-oidc.yaml`** — 信頼条件の sub が `main` 固定（StringEquals・ID 埋め込み形式）。`main` + `ai/*` を許可するよう `StringLike` へ拡張する（ID 埋め込み形式は維持。F-007）
5. **Amplify（appId=d1e1o87p5asykz）** — 現在 main のみ接続（productionBranch=main）。自動ブランチ作成を `ai/*` パターンで有効化し、branch 環境変数 `API_BASE_URL` に dev API エンドポイントを設定する（設定手段＝コンソール/CLI は [2]Plan で確定。git 管理外の AWS 側設定のため、実施手順をドキュメントに残す）
6. **`.ai-flow/project.yaml`** — `verify.method` を「dev 環境（デプロイ済み URL）での動作確認」に更新する
7. **CORS** — API 呼び出しはフロントのサーバー側（SSR/Server Actions）経由のみ（`knowledge-hub/frontend/src/lib/api.ts` の `API_BASE_URL` はサーバー側でのみ使用）。ブラウザから dev API を直呼びしないため、dev の `CorsAllowedOrigin` はデフォルト値（`http://localhost:3000`）のままでよい（AC で確定）
8. **DynamoDB 容量** — dev スタック追加でテーブル+GSI＝10RCU/10WCU 増。合計 prod 10/10 + dev 10/10 = 20/20 で常時無料枠 25RCU/WCU 以内

## 期待動作（正しい仕様）

- `ai/**` ブランチへ push（バックエンド/インフラ関連 paths の変更時）すると、GitHub Actions が `knowledge-hub-dev` スタックへ SAM デプロイし、dev API が利用可能になる
- `ai/*` ブランチへ push すると、Amplify が当該ブランチのフロントエンドを自動デプロイし、その SSR が dev API を参照する
- `main` への push は従来どおり prod（スタック `knowledge-hub`・Amplify main）へデプロイされ、**挙動・リソースとも一切変わらない**
- `ai/*` ブランチを削除すると Amplify のブランチ環境が自動削除される（dev SAM スタックは残る＝共有・常設）
- ai-flow の [6]動作確認は、デプロイ済み dev 環境の URL で実施する運用になる

## Acceptance Criteria（承認後は本節が正。変更には再承認が必要）

### 期待結果

- `ai/**` ブランチへの push（deploy.yml の paths 条件に合致する変更を含む）→ GitHub Actions が起動し、OIDC ロール `knowledge-hub-github-deploy` の Assume に成功し、SAM スタック `knowledge-hub-dev` がデプロイされる
- dev デプロイ後のスモークテスト → dev スタックの ApiEndpoint に対する `GET /api/articles` が 200 を返す
- `main` への push → 従来どおりスタック `knowledge-hub`（prod）へデプロイされる
- template.yaml のリソース名 `${AWS::StackName}` ベース化後、prod スタックでの解決結果が現行物理名と同一（`knowledge-hub-articles` / `knowledge-hub-api` / `knowledge-hub-http-api`）→ prod デプロイでリソースの**置換・再作成・削除が一切発生しない**（changeset が Modify のみ、または空）
- dev スタックのリソース物理名は `knowledge-hub-dev-articles` 等となり、prod と衝突しない
- Amplify: `ai/*` ブランチの push でブランチ環境が自動作成・デプロイされ、そのフロントエンド URL で記事一覧・詳細・作成・編集・削除・検索が dev API（SSR 経由）で動作する
- Amplify: `ai/*` ブランチの削除でブランチ環境が自動削除される
- Amplify の branch 用環境変数 `API_BASE_URL` が dev API エンドポイントを向く（main の `API_BASE_URL` は prod のまま）
- dev の `CorsAllowedOrigin` は template.yaml のデフォルト値のままとする（API 呼び出しは SSR 経由のみでブラウザ直呼びがないため。prod のパラメータ値は変更しない）
- `.ai-flow/project.yaml` の `verify.method` が「dev 環境（デプロイ済み URL）での動作確認」に更新されている
- DynamoDB のプロビジョンド合計が prod 10RCU/10WCU + dev 10RCU/10WCU = 20/20 で、常時無料枠 25RCU/WCU 以内に収まる
- Amplify 自動ブランチ作成の設定手順（AWS 側の git 管理外設定）がドキュメントに記録される（記載先は [7] で確定）

### 境界値

- ブランチ `ai/dev-env-deploy`（`ai/` + 1階層）→ Actions の dev デプロイ・OIDC Assume・Amplify 自動ブランチ作成のすべてが動作する
- `ai/` 配下にさらにスラッシュを含むブランチ（例 `ai/fix/foo`）→ Actions トリガー `ai/**` は一致する。OIDC（IAM StringLike の `*` はスラッシュにも一致）と Amplify のパターン仕様の一致範囲は [2]Plan で確認し、少なくとも `ai/{1階層}` が全経路で動作すればよい
- `main`・`ai/**` 以外のブランチへの push → いかなるデプロイも起動しない
- 複数の `ai/*` ブランチからほぼ同時に push → 共有 dev のため後勝ち（許容済み）。deploy.yml の concurrency により直列実行される（prod と dev のデプロイが相互をキャンセルしないこと）

### 異常系

- `mvn verify` 失敗時 → SAM デプロイに進まない（既存挙動を dev でも維持）
- スモークテスト失敗時 → workflow が失敗として終了する（dev/prod とも）
- `ai/**` の workflow が誤って prod スタック（`knowledge-hub`）へデプロイすることがない（ブランチ振り分けの誤動作は Critical。[5]レビューの必須観点）
- OIDC 信頼条件の拡張に誤りがある場合 → AssumeRole が拒否され workflow が失敗する（prod 側の main デプロイが巻き添えで拒否されないこと）

### 禁止事項（この修正でやってはいけないこと）

- DynamoDB をオンデマンド課金モードに変更しない。プロビジョンド合計 25RCU/WCU を超えない（constraints / guard-rules）
- `template.yaml`・`samconfig.toml`・`github-oidc.yaml` は ASCII のみで記述する（前例 F-005）
- prod スタックのリソース置換・再作成・削除を伴う変更をしない（API エンドポイント URL の変化を含む）
- GitHub に長期 AWS アクセスキーを保存しない（OIDC 方式を維持）
- 秘密情報（AWS 認証情報等）のハードコード禁止
- deploy.yml に GitHub Environment 指定を追加しない（追加する場合は OIDC 信頼条件とセットで設計。前例 F-006）
- OIDC sub の ID 埋め込み形式（`owner@ownerId/repo@repoId`）を崩さない（前例 F-007）
- ai-dev-flow 配布物（`.ai-flow/flow/` `roles/` `templates/` 等）へプロジェクト固有値を書き込まない（`project.yaml` は導入先設定ファイルなので変更可）
- フロントエンドの SPA 化禁止（本件でフロントのコード変更が生じる場合も SSR + Server Actions を維持）

### 変更してはいけない既存仕様

- prod スタック名 `knowledge-hub` と物理リソース名 3 点（`knowledge-hub-articles` / `knowledge-hub-api` / `knowledge-hub-http-api`）、および prod API エンドポイント URL
- main push による prod デプロイのトリガー条件（対象 paths 含む）と、mvn verify → デプロイ → スモークテストの流れ
- OIDC ロール名 `knowledge-hub-github-deploy` と main ブランチの信頼（拡張のみ。縮小・削除しない）
- Amplify main ブランチ（本番フロント）のビルド設定・環境変数・URL（`https://main.d1e1o87p5asykz.amplifyapp.com`）
- prod の `CorsAllowedOrigin` パラメータ値（`https://main.d1e1o87p5asykz.amplifyapp.com`）
- API エラーレスポンス形式 `{"message": ..., "errors": [...]}`（本件でバックエンドのコード変更は想定しないが、外部仕様として維持）
