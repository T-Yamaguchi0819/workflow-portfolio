# knowledge/ — ナレッジ運用ルール

フローを回すたびに得られる「確認済みの回答・判断・失敗」をファイルに蓄積し、**次回以降の確認・調査・事故を減らす**ための置き場。3ファイルの役割分担が重要。

| ファイル | 内容 | 共有 |
|---------|------|------|
| `defaults.md` | チーム共通の**運用値・確認済み回答**（書式・配置・標準処理） | コミット対象（個人名・マシン固有値を書かない） |
| `defaults.local.md` | **個人・マシン固有**の設定（担当者名・ローカル環境・ビルド手順） | コミット対象外（.gitignore 済み。`defaults.local.example.md` から生成） |
| `precedents.md` | **判断履歴DB**（設計判断・記載慣行・失敗事例の構造化カタログ) | コミット対象 |

## 運用ルール

1. **確認の前に引く**: 各フェーズはユーザーへ確認する前に必ず defaults／precedents を参照し、記載済み項目は確認せずデフォルト適用する（適用した項目はゲートで事後報告）
2. **確認したら書く**: ユーザー確認で新たに確定した値・判断は、その場で該当ファイルへ追記する（チーム共通→defaults.md／個人・環境→defaults.local.md／設計判断・慣行・失敗→precedents.md）。事実のみ・確認日とタスクNoを併記する
3. **失敗→ルール化のサイクル**: 失敗事例（AI の誤り・見落とし・人間による修正）は precedents.md の失敗事例節に記録する。**同種の失敗が3回**記録されたら、次のいずれかへの「昇格」をユーザーに提案する:
   - 正規表現で機械検出可能 → `guards/guard-rules.json` に検査ルール追加
   - 手順・判断の問題 → フェーズ定義（`flow/`）または役割定義（`roles/`）に制約を追記
   - 運用値の問題 → defaults.md に追記

このサイクルにより、案件をこなすほど自動化基盤そのものが賢くなる。
