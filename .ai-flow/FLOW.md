# AI修正フロー統括（FLOW.md）

**あなたの役割**: 本プロジェクトの修正タスクを、`flow/` の各フェーズ定義に従い**フェーズ毎に順次実行**して統括すること。各フェーズはファイル受け渡しで自己完結しており、コンテキスト消失・セッション切替をまたいでも `_state.md` と成果物ファイルから状態を復元できる。

プロジェクト固有の値（技術スタック・コマンド・コミット書式・リスク分類・ドキュメント構成）は **`project.yaml`** が正。フローを実行する前に必ず読むこと。

## 大原則（全フェーズに伝播させる）

- **仮実装禁止**（本実装のみ。ダミー値・ハードコードによる見せかけ再現をしない）
- **不明点・既存実装との矛盾は推測で進めず、必ずユーザー確認**（未解決事項として貯めてゲートで確認）
- **コミット/push/PR の扱いは `project.yaml` の `git.commit_policy` が正**（`manual`: ユーザーが明示的に指示した場合のみ／`auto`: フェーズ完了ごとに自動コミット・push し、[8] で PR を発行。最終承認は PR マージ）。モードに関わらず、修正は必ず新ブランチ（`branch_prefix`）で行い、**デフォルトブランチへの直接コミット・push・マージは絶対にしない**（マージは常に人間が行う）
- プロジェクト固有の禁止事項は `project.yaml` の `constraints` と `guards/guard-rules.json` が正。コミット前に `guards/verify_diff.py` が機械検査する
- **記述の使い分け**: コードには **How**（命名・構造で表現）／テストコードには **What**（テスト名・アサーションで表現）／コミットログには **Why**（背景・目的を本文に記載）／コードコメントには **Why not**（他の自然な実装を採らなかった理由のみ）

## 作業ディレクトリ（状態置き場）

```
.ai-flow/work/{タスク名}/
├── _state.md                    # タスク状態（templates/_state.md からコピー）
└── No{N}_{機能名}/              # 要件単位の成果物ディレクトリ
    ├── 要件.md      # [1] 要件＋Acceptance Criteria（承認済みが正）
    ├── plan.md      # [2] 修正Plan（変更分類・リスク/規模判定含む）
    ├── test.md      # [3] 先行作成したテストの記録
    ├── impl.md      # [4] 実装記録（※レビュアーには見せない）
    ├── review.md    # [5] 独立レビューの指摘と対応
    ├── verify.md    # [6] 動作確認記録（エビデンスパス）
    ├── docs.md      # [7] ドキュメント反映記録
    └── 実績.md      # [8] 実績測定（templates/実績.md からコピー）
```

各フェーズは冒頭で `_state.md` と前フェーズ成果物を読んでから作業する。ゲートで得たユーザーの回答・承認は、統括が **`_state.md` の「解決済みの確認事項」へ追記してから**次フェーズを開始する（回答の受け渡しは必ずこのファイル経由。プロンプトだけに書くとコンテキスト消失時に失われる）。

## 規模判定（S/M/L）とリスク判定

[2]Plan で確定し `_state.md` に記録する（暫定判定は [1] 時点で置く）。

### 規模

| 規模 | 目安 |
|------|------|
| **S** | 文言・表示のみの修正、1〜2ファイルのロジック修正で影響範囲が閉じているもの |
| **M** | 通常の不具合修正・小機能追加（複数ファイル・ロジック変更あり） |
| **L** | 大規模・影響範囲大（複数画面/機能、DB・外部I/F に波及、正式ドキュメント改版必須） |

### リスク

`project.yaml` の `risk` 分類が正。目安:

| 変更内容 | リスク |
|---------|--------|
| コメント・画面文言 | Low |
| 単一機能のロジック | Medium |
| SQL・データアクセス層・外部API | High |
| 認証・認可、DBスキーマ、決済・機微データ | Critical |

**リスク High 以上は規模に関わらず [5]独立レビューを必須**とし、Critical は加えて**人間レビューを必須**とする（ゲートで明示的に依頼する）。

| 4 | `flow/4-implement.md` | 実装（Plan 準拠・スコープ限定） | ✓ | ✓ | ✓ |
| 5 | `flow/5-review.md` | **独立レビュー**（コンテキスト分離） | —※ | ✓ | ✓ |
| 6 | `flow/6-verify.md` | 動作確認・エビデンス取得 | ✓ | ✓ | ✓ |

## ゲート（ユーザー承認で停止するポイント）

| タイミング | 確認内容 |
|-----------|---------|
| **[1] の後（AC承認）** | Acceptance Criteria の承認。**承認前にテスト・実装へ進まない** |
| **[2] の後（Plan承認）** | 修正方針・変更分類・リスク/規模判定の承認。実装着手前 |
| **[5] の後** | レビュー結果と対応の報告（未解消の指摘があれば判断を仰ぐ） |
| **[7] の前** | ドキュメント変更内容の確認（プロジェクトの検証手順があれば実施結果も） |
| **[8] の後（完了）** | `manual`: 全成果物の提示・実績報告・コミット要否の確認／`auto`: PR と AI PR レビュー結果の報告（最終承認は PR マージ＝人間） |

- 確認事項は**ゲートまで貯めて一括で質問**する（1問ずつ小出しにしない）。`knowledge/defaults.md` に記載済みの項目は確認せずデフォルト適用し、ゲートで**事後報告**する
- フェーズ実行者が**未解決事項**を返した場合は、フェーズ途中でも停止してユーザーに確認する

## コミットポリシーと PR 運用

`project.yaml` の `git.commit_policy` で選択する。どちらのモードでも、guards（pre-commit）が ERROR を出したコミットは違反を解消するまで通さない（誤検知と考える場合も独断で `--no-verify` 等により回避せず、ユーザーに確認する）。

| モード | コミット/push | 最終承認 |
|--------|--------------|---------|
| `manual` | ユーザーが明示的に指示した場合のみ（[8] 完了ゲートで要否確認） | 完了ゲート（会話） |
| `auto` | **フェーズ完了ごとに**自動コミット・push（`commit_format` 準拠・本文に Why） | **PR マージ**（人間が行う） |

`auto` の前提: デフォルトブランチにブランチ保護（直 push 禁止・PR レビュー必須）が設定されていること。未設定なら導入時に設定するか `manual` を使う。

### `auto` のレビューは3層（責務を重複させない）

| 層 | タイミング | 責務 |
|---|-----------|------|
| [5] 独立レビュー | PR 前（内側ループ） | AC への反例探し・変更禁止侵害。**修正コストが安いうちに**直す |
| AI PR レビュー | PR 発行後（[8]） | 指摘対応後の**最終 diff 全体**を、[5] とも実装とも別のコンテキストで検査（スコープ外変更の混入・修正の副作用） |
| 人間レビュー | マージ前 | **AI に判定できないもの**に集中: AC 自体の妥当性・ビジネス判断・外部仕様との整合。リスク Low/規模 S はサマリ確認のみでよく、High 以上は精読必須（Critical の人間レビュー必須はこの層で満たす） |

- PR 本文は `templates/pr.md` を使い、人間レビュアーの観点（上記の分担）を PR 上に明記する（「AI が2回見たから大丈夫」というラバースタンプ化の防止）
- **マージは常に人間が行う。AI は自分の PR をマージしない**
- **マージ後の還流**: 人間レビューでの指摘件数・内容を `実績.md`（「AIレビュー後に人間が発見した問題数」）へ追記し、失敗事例は `precedents.md` へ記録する（ルール化サイクルの入力）

## GitHub Issue ミラー（人間向け可視化・承認チャネル）

`project.yaml` の `issue_sync.enabled: true` の場合のみ実施する。**正はあくまでファイル**（`_state.md`・成果物）であり、Issue は人間向けの進捗ミラーと承認チャネル。Issue と `_state.md` が食い違った場合はファイルが正。Issue の操作（作成・コメント・クローズ）は**統括のみ**が `gh` CLI で行う。

- **作成**: [0]初期化でタスク1件につき Issue を1件作成し、Issue 番号を `_state.md` の基本情報に記録する
- **同期タイミング**: 統括が**各フェーズ完了時とゲート到達時**に `gh issue comment` で投稿する。内容は①進捗マトリクスの現在値 ②確認事項（ゲートの場合。会話で提示するものと同内容）③成果物への参照（ブランチ名＋ファイルパス）。**成果物の本文は Issue へ転記しない**（長文はファイルが正。参照で足りる）
- **承認の受け取り**: ゲートの回答・承認は会話でも Issue コメントでもよい。Issue で受けた場合も、統括が `_state.md` の「解決済みの確認事項」へ**転記してから**次フェーズを開始する（フェーズ実行者への受け渡しは従来通りファイル経由。Issue を読ませない）
- **クローズ**: `manual` では [8] の完了ゲート通過後、完了サマリ（実績・成果物一覧）をコメントしてから Issue をクローズする。`auto` では完了サマリのコメントのみ行い、クローズは PR 本文の `Closes #{番号}` によりマージ時に自動で行わせる
- **縮退**: `gh` が使えない・投稿が失敗した場合は**同期をスキップして続行**し、次ゲートでユーザーに報告する。Issue 同期の失敗を理由にフローを止めない
- **コンテキスト分離との関係**: Issue には実装経過が載るため、[5]独立レビューのレビュアーには **Issue を渡さない・読ませない**（レビュアーへの入力は `flow/5-review.md` の表が正）

## 独立レビューの実行形態（エージェント別）

[5]独立レビューは**実装とコンテキストを分離**して実行する。レビュアーに渡してよいのは **要件.md（AC）・plan.md・コード diff・`roles/code-reviewer.md`** のみ。impl.md（実装記録）・実装時の会話・思考過程は渡さない（実装者の誤った仕様解釈をレビュアーが引き継ぐことを防ぐ）。

| エージェント | 実行形態 |
|-------------|---------|
| Claude Code | code-reviewer **サブエージェント**を起動（コンテキストが自動分離される） |
| Codex | **新しいセッション**を開き、レビュー用プロンプト（adapters/codex/prompts）で実行 |
| Cursor | **新しいチャット**を開き、レビュー用コマンドで実行 |

サブエージェント/別セッションで実行する場合の共通指示: 「フェーズ定義ファイルを読み、その手順を厳密に実行せよ。あなたはユーザーと直接対話できない。フェーズ定義に『ユーザーに確認』とある事項は、推測で進めず**未解決事項として返して終了**すること（回答済みの事項は `_state.md` の『解決済みの確認事項』を参照）。完了後、生成・更新したファイルと未解決事項を簡潔に返すこと。」

## 差し戻し・エスカレーション

- **レビュー差し戻しの上限**: 同一指摘についてレビュー⇔修正は**最大2往復**。解消しない場合は修正試行をやめ、進捗マトリクスを 🛑 にして「未解決の確認事項」に記載し、ユーザーの判断を仰ぐ
- **テスト失敗の上限**: [6] で同一テストの失敗→修正を**3回**繰り返しても解消しない場合、同様にエスカレーションする（場当たり的な修正の連鎖を防ぐ）
- **複数要件（No）がある場合**: No 単位で [2]〜[8] を回す。No 間は**原則直列**で処理（状態ファイル・共有リソースの競合防止。並列化する場合は成果物が完全に独立していることを確認する）

## ナレッジ運用

| ファイル | 内容 | 参照タイミング |
|---------|------|--------------|
| `knowledge/defaults.md` | チーム共通の運用値・確認済み回答 | 全フェーズ。ユーザーへ確認する**前に**必ず引く |
| `knowledge/defaults.local.md` | 個人・マシン固有の設定（コミット対象外） | 同上 |
| `knowledge/precedents.md` | **判断履歴DB**（設計判断・記載慣行・失敗事例） | [2]Plan・[5]レビュー・[7]ドキュメントの調査前に**最初に**引く |

- 新たな運用判断をユーザーに確認したら、該当ファイルへ**追記**する（次回以降の確認・調査を不要にする）
- **失敗事例のルール化サイクル**: [8] で失敗事例を precedents.md に記録し、**同種の問題が3回起きたら** `guards/guard-rules.json` への機械検査ルール追加を提案する（案件をこなすほど基盤が賢くなる）

## 実績測定とフロー評価

[8] で `実績.md`（テンプレートあり）に記録する。主要 KPI は「AI が何分動いたか」ではなく**人間工数が何％減ったか**。手戻り回数・初回PASS率・AIレビュー後に人間が発見した問題数も記録し、フロー自体の改善判断に使う。

- **記録の正は 実績.md の metrics ブロック**（機械可読 YAML。テンプレート参照）。null 可・推測値禁止
- **集計と KPI 判定**: `python .ai-flow/evaluate_flow.py` が全タスクの実績を集計し、`project.yaml` の `evaluation.targets` と突合したレポート（KPI 判定・規模/リスク別内訳・直近傾向・要注意タスク）を生成する
- **振り返りサイクル**: 完了タスク数が `evaluation.review_cycle` の倍数に達したら、[8] でレポートを生成して完了ゲートでユーザーに提示し、未達 KPI の要因と対策（defaults/precedents への追記・guard-rules 昇格・フェーズ定義の改善提案）を確認する
- **評価も還流させる**: 未達 KPI の対策として確定した判断は、通常のナレッジと同様に defaults/precedents へ記録する（評価して終わりにしない）
