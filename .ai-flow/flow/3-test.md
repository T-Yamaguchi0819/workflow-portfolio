# [3] テスト先行作成（期待値を先に固定する）

**目的**: 実装前に、**承認済み Acceptance Criteria を根拠として**テストを作成する。テストは AC の実装物であり、期待値の正しさの根拠は常に AC（要件.md）に遡れること。実装コードに合わせてテストを書くこと・実装後に期待値を「実際の動作」に合わせて書き換えることを禁止する。

## 前提（最初に読む）

1. `_state.md`・対象 No の `要件.md`（**AC が承認済みであることを確認**。未承認なら作業せず未解決事項として返す）・`plan.md`
2. `.ai-flow/project.yaml`（`build.test_command`・`build.test_location`・`verify.method`）
3. 既存テストの書き方（同一プロジェクトの類似テストを1つ以上読み、命名・構成を踏襲する）

## 手順

1. AC の各項目（期待結果・境界値・異常系）を**テストケースに対応付ける**。対応表を `test.md` に記録する（AC 側に対応するテストが無い項目を可視化する）
2. `plan.md` の動作確認観点（正常系・回帰・異常系・境界値・権限別）のうち、自動化可能なものをテストコードとして作成する。自動化できない観点は [6]動作確認の手動手順として `test.md` に記録する
3. この時点でテストを実行し、**修正前は期待通り失敗すること**（不具合修正の場合）を確認・記録する。修正前から PASS するテストは期待値がおかしい可能性が高い（AC と突き合わせて見直す）
4. `No{N}_{機能名}/test.md` に、作成したテストのパス・AC対応表・実行結果を記録する

**規模 S の場合**: 自動テストが現実的でない修正（文言のみ等）は、[6] で確認する手動観点のリストを `test.md` に書くだけでもよい（その旨を記録する）。

## 成果物

- テストコード（`project.yaml` の `test_location` 準拠）
- `No{N}_{機能名}/test.md`（AC⇔テスト対応表・修正前実行結果）

## 完了条件

- AC の全項目がテスト（自動）または手動確認観点のどちらかに対応付いている
- テスト名・アサーションが **What**（何を満たすべきか）を表現している
