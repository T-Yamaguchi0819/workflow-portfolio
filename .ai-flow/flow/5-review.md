# [5] 独立レビュー（コンテキスト分離）

**目的**: 実装者から独立した視点でコードレビューを行う。実装者の仕様解釈を引き継ぐと「同じ誤解を共有したままレビュー PASS」になるため、**レビュアーには実装者の作業記録・思考過程を渡さない**。

## 実行形態（統括向けの指示）

- **Claude Code**: code-reviewer サブエージェントで実行（コンテキスト自動分離）
- **Codex / Cursor**: 実装とは**別のセッション/チャット**を開き、本ファイルを読ませて実行する
- リスク **Critical** の場合、AI レビューに加えて**人間レビューを必須**とし、ゲートで明示的に依頼する

## レビュアーへの入力（これ以外を渡さない・読まない）

| 渡すもの | 渡さないもの |
|---------|-------------|
| `要件.md`（承認済み AC） | `impl.md`（実装記録） |
| `plan.md`（変更分類・影響範囲） | 実装時の会話・思考過程 |
| コード diff（`git diff`） | — |
| `.ai-flow/roles/code-reviewer.md`・`project.yaml`・`knowledge/precedents.md` | — |

## レビュー観点（roles/code-reviewer.md に従う）

1. **AC への反例探し**: 「実装が正しいか」ではなく「**AC に対して反例がないか**」を探す（境界値・異常系・権限差異で AC を破る入力・状態を挙げてみる）
2. **変更禁止リストの侵害**: plan.md の「変更禁止」「要確認」に触れていないか
3. **スコープ外変更**: Plan に無い変更・無関係な整形が紛れていないか
4. **禁止/必須パターン**: `project.yaml` の `constraints` 違反（機械検査できない種類のもの。機械検査可能なものは guards が担う）
5. **副作用・回帰**: 影響範囲（依存レイヤ連鎖）に対する考慮漏れ

## 手順

1. レビュアーが上記入力のみを読み、指摘を「重要度（要修正／推奨／備考）・根拠（AC/制約のどこに反するか）」つきで返す
2. 統括は指摘を `No{N}_{機能名}/review.md` に記録し、**要修正**があれば [4] へ差し戻す（修正後、diff を更新して再レビュー）
3. **同一指摘の差し戻しは最大2往復**。解消しない場合は 🛑 でエスカレーションし、ユーザーの判断を仰ぐ
4. レビュー中に確定した設計判断・記載慣行は `knowledge/precedents.md` へ追記する

## 成果物

- `No{N}_{機能名}/review.md`（指摘・対応・往復回数）

## ゲート（必須）

レビュー結果（指摘と対応、未解消事項）をユーザーに報告してから [6] へ進む。指摘ゼロの場合も「何を確認して問題なしとしたか」を報告する。
