# [2] 調査・修正Plan 作成

**目的**: 実装前に修正箇所・影響範囲を調査し、**変更分類（変更対象／変更可能／変更禁止／要確認）とリスク・規模判定**を含む Plan を作成してユーザー承認を得る。

## 前提（最初に読む）

1. `_state.md`・対象 No の `要件.md`（承認済み AC）
2. `.ai-flow/project.yaml`（`constraints`・`risk`・`docs`）
3. `.ai-flow/knowledge/precedents.md`（**個別調査の前にまず引く**。過去の判断・記載慣行を再利用する）
4. `.ai-flow/knowledge/defaults.md`

## 手順

1. **実装調査**: 対象機能の既存実装を読み、修正箇所を特定する（推測で書かない。実コードを参照して確認する）。類似機能の実装パターンがあれば踏襲候補として記録する
2. `templates/plan.md` をコピーして `No{N}_{機能名}/plan.md` を作成し、以下を記入する:
   - 対象ファイル一覧と、ファイルごとの具体的な変更方針
   - **影響範囲**: 呼び出し元・関連機能・DB・権限差異に加え、**依存レイヤの連鎖**（例: Controller → Service → Repository → SQL → DB のどこまで届くか）を明示する
   - **変更分類**: 触れる範囲を「変更対象／変更可能／**変更禁止**／要確認」に分類する。特に DB 項目・外部I/F・エラーメッセージ・権限・ログ・トランザクション・既存の特殊仕様は明示的に扱う（レガシーでは「不要に見えるが外部仕様」が多い）
   - **リスク判定**: `project.yaml` の `risk` 分類に照らして Low/Medium/High/Critical を判定する
   - **規模判定**: S/M/L を確定する（FLOW.md の基準）。リスク High 以上は規模に関わらず [5]独立レビュー必須、Critical は人間レビューも必須
   - 動作確認の観点（正常系・回帰・異常系・境界値・権限別）
   - ドキュメント反映方針（`docs.enabled` の場合。**前例調査**として precedents.md → 類似機能のドキュメントの順で調べ、反映要否と根拠を記載）
3. `_state.md` の規模・リスク・進捗を更新する

**規模 S の場合（簡易版）**: 対象ファイル・変更方針・変更分類・リスク判定のみ必須。

## 成果物

- `No{N}_{機能名}/plan.md`
- `_state.md` 更新（規模・リスク確定）

## ゲート（必須）

**Plan 承認ゲート**: 修正方針・変更分類・リスク/規模判定（およびフェーズのスキップ提案があればそれ）をユーザーに提示し、**承認を得てから実装系フェーズへ進む**。precedents.md に無い設計判断をユーザー確認で確定させた場合は、承認後に precedents.md へ追記する。
