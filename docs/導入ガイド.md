# 導入ガイド

新しいプロジェクトへ ai-dev-flow を導入する手順。所要の目安は初回 1〜2 時間（大半は project.yaml と guard-rules.json の記入）。

## 前提

- git リポジトリであること（複数リポジトリ構成でも可）
- 使うエージェント: Claude Code / Codex / Cursor のいずれか（複数併用可）

### 必要なツール・ライブラリ

有効化する機能によって必要なものが変わる。**次のコマンドで、自プロジェクトの設定に対する過不足を確認できる**（導入の最初と、Step 2 で project.yaml を記入した後に実行する）:

```
python .ai-flow/check_env.py
```

| ツール/ライブラリ | レベル | 必要になる機能 | 導入方法 |
|------------------|--------|---------------|---------|
| Python 3.8+ | 必須 | guards（禁止パターンLint）・各スクリプト（無いとフローは動くが機械検査がスキップされる） | python.org |
| git | 必須 | ブランチ運用・pre-commit フック | — |
| gh CLI | 条件付き必須 | `issue_sync`（Issue ミラー）・`commit_policy: auto`（PR 発行/レビュー） | cli.github.com → `gh auth login` |
| openpyxl・PyYAML | 条件付き推奨 | Excel 書式テンプレートの抽出/検査（Step 6） | `pip install openpyxl pyyaml` |
| pywin32 | 任意 | Excel COM 書き込み（`excel_write_policy`。Windows のみ） | `pip install pywin32` |

## Step 1: 本体のコピー

本リポジトリの `.ai-flow/` ディレクトリを、対象プロジェクトのルートへそのままコピーする。

```
対象プロジェクト/
├── .ai-flow/          ← コピー
├── （既存のソース）
└── ...
```

複数リポジトリをまとめたワークスペース構成（例: `workspace/repo-a`・`workspace/repo-b`）の場合は、ワークスペースのルートに置き、guard-rules.json の `repos` に各リポジトリの相対パスを列挙する。

## Step 2: project.yaml の記入（最重要）

`.ai-flow/project.yaml` の `TODO:` をすべて埋める。特に重要なのは:

| 節 | 内容 | 手を抜くと起きること |
|----|------|--------------------|
| `constraints` | 禁止・必須・事故多発ポイント | AI が既存の暗黙ルールを破る |
| `risk` | Critical/High の定義 | 危険な変更が軽いレビューで通る |
| `build`・`verify` | ビルド・テスト・動作確認の方法 | フェーズ [3][4][6] が毎回試行錯誤する |
| `git` | ブランチ・コミット規約 | コミットログが揃わない |

記入のコツ: 過去の障害・レビュー指摘・新人がやりがちなミスを思い出し、「機械検出できるもの」は Step 3 の guard-rules.json へ、「文脈判断が要るもの」は `constraints` へ書き分ける。

**コミット/PR の承認モード（任意）**: `git.commit_policy` はデフォルト `manual`（コミット/push はユーザー指示時のみ）。GitHub の PR 運用があるプロジェクトでは `auto` にすると、フェーズ完了ごとに自動コミット・push され、[8] で PR が発行されて最終承認が PR マージに移る（[5]独立レビュー → AI PR レビュー → 人間レビューの3層。詳細は FLOW.md の「コミットポリシーと PR 運用」節）。**前提として、デフォルトブランチのブランチ保護（直 push 禁止・PR レビュー必須）を必ず設定すること**。未設定のまま `auto` にすると、マージ承認が紳士協定になり `manual` より弱くなる。

**記入後の確認**: `python .ai-flow/check_env.py` を再実行し、有効化した機能（`issue_sync`・`commit_policy: auto`・`docs`）に必要なツールが揃っているか確認する。

**GitHub Issue で進捗を可視化したい場合（任意）**: `issue_sync.enabled: true` にする。タスク1件につき Issue が1件作成され、フェーズ完了・ゲート到達のたびに進捗と確認事項がコメントされる（承認は Issue コメントでも可）。`gh` CLI のインストールと `gh auth login` が前提。正はあくまでファイル側で、`gh` が使えない環境では自動的にスキップされる。運用ルールの詳細は FLOW.md の「GitHub Issue ミラー」節を参照。

## Step 3: guard-rules.json の定義

`.ai-flow/guards/guard-rules.json` の `example-*` ルールを自プロジェクトの禁止パターンに置き換える。動作確認:

```
python .ai-flow/guards/verify_diff.py --repo <リポジトリ>
```

わざと違反行を追加して ERROR が出ること・除去して 0 件になることを確認する。

## Step 4: git pre-commit フックの導入

```
# Windows
powershell .ai-flow\guards\hooks\install-git-hooks.ps1
# macOS / Linux
sh .ai-flow/guards/hooks/install-git-hooks.sh
```

guard-rules.json の `repos` 全部に導入される。既存の pre-commit がある場合は警告が出るので手動マージする。**このフックがエージェント非依存の最終防壁**なので必ず導入する。

## Step 5: エージェント別アダプタの導入

使うエージェントの `adapters/{agent}/README.md` に従う（複数導入可。フロー・成果物は共有される）:

- **Claude Code**: コマンド・エージェント定義・PreToolUse フック・CLAUDE.md スニペット
- **Codex**: AGENTS.md スニペット・カスタムプロンプト2種
- **Cursor**: rules（.mdc）・コマンド2種

## Step 6: ドキュメント書式のテンプレート化（`docs.enabled` のプロジェクトに推奨）

正式ドキュメントが Excel の場合、書式を「style YAML（検証用）＋雛形 .xlsx（生成用）」のハイブリッドでテンプレート化する（役割分担は `.ai-flow/docs-style/README.md`）。

1. **対象ドキュメントの棚卸し**: 設計書だけでなく、**テスト仕様書・運用手順書・障害報告書等も含めて**列挙し、`project.yaml` の `docs.targets` に記入する
2. **サンプルの確認**: 対象ごとに代表サンプル1件の有無を確認し、`sample` にパスを記入する（無い対象は「なし」と明記。未記入のまま運用を始めても [0]初期化で確認されるが、導入時に済ませる方が立ち上がりが速い）
3. **抽出と確定**: `pip install openpyxl pyyaml` のうえ `python .ai-flow/guards/extract_excel_style.py <サンプル.xlsx>` で下書きを生成し、**人間がレビューして確定**する（styles の命名・許可フォントの絞り込み・patterns の追記）。確定した YAML を `docs-style/` へ置き、`docs.targets[].style` に記入する
4. **雛形の切り出し**: 新規作成が発生し得る単位（機能節・テストケース表等）を雛形 .xlsx として `docs-style/` へ置き、`templates` に記入する
5. **検査の動作確認**: 対象にわざと許可外フォントのセルを追加し、`verify_excel_style.py` が ERROR を出すこと・除去して 0 件になることを確認する
6. **書き込み経路の固定**: `docs.excel_write_policy` を記入する（openpyxl での保存は図形・グラフを破壊し得るため原則禁止。Windows なら Excel COM 推奨）。機械強制したい場合は `pretooluse_guard.py` の拡張ポイントに openpyxl 保存ブロックを追記する（コメントに実装例あり）

## Step 7: ナレッジの初期投入（任意・推奨)

既存プロジェクトに運用知見がある場合、最初に移植しておくと立ち上がりが速い:

- 確認済みの運用値（書式・配置・標準処理）→ `knowledge/defaults.md`
- 過去の設計判断・レビューでよく出る指摘 → `knowledge/precedents.md`（構造化フォーマットに合わせて）
- 過去の障害・AI の失敗 → `precedents.md` の失敗事例節（ルール化済みなら guard-rules.json にも）

## Step 8: 動作確認（パイロット案件）

小さめの実案件（規模 S〜M）を1件、フローで流して確認する:

- [ ] [1] AC 承認ゲートで停止するか
- [ ] [2] Plan に変更分類・リスク/規模判定が入るか
- [ ] [5] レビューがコンテキスト分離で実行されるか（Codex/Cursor は別セッション）
- [ ] 禁止パターン入りのコミットが pre-commit でブロックされるか
- [ ] [8] 実績.md とナレッジ追記が行われるか
- [ ] （`issue_sync` 有効時）[0] で Issue が作成され、ゲートで進捗コメントが投稿され、[8] でクローズされるか
- [ ] （`commit_policy: auto` 時）フェーズ完了ごとにコミットされ、[8] で PR＋AI PR レビューコメントが作成され、マージ前に停止するか
- [ ] （`docs.targets[].style` 設定時）[7] で書式検査が実行され、許可外フォントの混入が検出されるか

## 運用開始後

- 毎タスク [8] で `実績.md` の metrics ブロックを記録する。`evaluation.review_cycle`（既定 10 タスク）ごとに `python .ai-flow/evaluate_flow.py` でフロー評価レポート（KPI 判定・規模/リスク別内訳・傾向・要注意タスク）を生成し、チームで振り返る。`evaluation.targets` の目標値（削減率・初回PASS率・人間追加指摘・手戻り）は自チームの水準に合わせて調整する
- 同種の失敗が 3 回記録されたら guard-rules / flow / roles への「昇格」を行う（`knowledge/README.md` のサイクル）
- フェーズ定義（`flow/`）自体のプロジェクト固有カスタマイズは最小限にする（本体を汚すと配布元の改善を取り込みにくくなる。固有事項はできる限り project.yaml・knowledge・guard-rules へ）
